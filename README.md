# 鲜达团餐 · 便利店企业团餐预订与临期鲜食调拨平台

## 原始需求

### 本轮需求（临期鲜食优先调拨，原文）

增加临期鲜食优先调拨。某门店便当即将临期但仍符合团餐时间要求，平台可推荐折扣方案给企业行政。企业接受后，商品批次、折扣、温控和售后责任会写入团餐单。临期调拨会标记到每份餐食，企业端能看到折扣原因和售后规则。折扣方案会保留企业确认，后续售后不能把临期误认为质量问题。企业确认会进入月结附件和售后说明。

### 上一轮需求（餐食变质售后，原文）

增加餐食变质售后。企业员工反馈饭团异味或便当变质时，平台收集商品批次、签收时间、温控照片和食用人员。客服可批量退款、补送或触发同批次门店下架。同批次下架后，平台会检查是否仍有门店库存和未配送团餐。同批次库存检查会生成门店任务，未处理门店会被运营提醒。门店任务会显示处理截止时间、责任班次和复核人。

### 更早一轮需求（临时加餐，原文）

增加企业临时加人数。企业在送达前一小时增加 30 份餐食时，平台检查周边门店库存、制作批次、配送容量和发票金额。确认后，追加商品、送达时间和差额费用同步更新。追加餐食如果涉及过敏或素食，门店必须按企业名单重新贴标。临时追加会同步到门店拣货清单，避免漏贴某一类特殊餐标。特殊餐标会同步给配送员和企业签收人。

### 初始需求（平台一期，原文）

建设便利店企业团餐预订与临期鲜食调拨平台，可采用 Vue 3、NestJS 和 PostgreSQL。企业行政提交会议、培训或加班餐需求时，平台记录人数、餐标、素食、过敏、送达时间、发票和备用联系人。平台根据附近门店库存、鲜食生产批次、配送能力、临期商品、企业历史偏好和门店高峰时段生成供餐方案。门店备货时记录饭团、便当、三明治、咖啡、饮料和水果的批次、温控和保质期；配送员取货后记录出库、保温箱、路线和签收。若企业临时增减人数、门店库存不足、鲜食临期、配送迟到、发票信息错误或员工反馈餐食变质，平台要把企业行政、门店、仓配、客服和财务放在同一团餐单里处理。交付完成后，实际消费、退货、临期调拨、赔付、发票和企业复购进入档案。平台还要处理企业长期合同、门店临时缺员、供应商延迟到货、午高峰散客冲突和发票月结。团餐既是零售业务，也是企业客户服务，交付失败会影响企业复购和门店评价。企业团餐还会影响门店正常顾客购物，平台需要提醒门店在团餐备货、散客销售和临期处理之间做平衡。企业客户复购前，平台会展示历史准点率、售后次数、发票错误和餐食偏好，行政可以据此调整下一次团餐套餐。

## 技术栈与架构

- **前端**：Vue 3 + Vite + Element Plus + Pinia + ECharts（构建产物由后端统一托管）
- **后端**：NestJS 10 + TypeORM + JWT 认证 + 角色守卫
- **数据库**：PostgreSQL 16（仅 compose 内部网络访问，不发布到宿主）
- **部署**：根目录多阶段 `Dockerfile`（非 root 用户 + HEALTHCHECK）+ `docker-compose.yml`（app + db）

```
┌────────────┐      ┌─────────────────────────┐      ┌────────────┐
│  浏览器     │ ───▶ │  app 容器 (Node 20)      │ ───▶ │  db 容器    │
│  Vue 3 SPA │      │  NestJS API + 静态托管   │      │ PostgreSQL │
└────────────┘      └─────────────────────────┘      └────────────┘
                    宿主端口 ${CC_PUBLISH_PORT}:3000   仅内部网络
```

## 一键启动（验证方式 = 宿主 docker compose up）

```bash
# 1. 准备环境变量（可选，不建 .env 也能用默认值启动）
cp .env.example .env

# 2. 构建并启动（项目名由 COMPOSE_PROJECT_NAME 固定，端口由 CC_PUBLISH_PORT 注入）
docker compose up -d --build

# 3. 查看应用实际映射端口
docker compose port app 3000
# 浏览器访问 http://localhost:<映射端口>   （容器内验证可用 http://host.docker.internal:<映射端口>）

# 4. 健康检查
curl http://localhost:$(docker compose port app 3000 | cut -d: -f2)/api/health

# 5. 验证结束后释放资源
docker compose down
```

首次启动且数据库为空时，会自动写入演示种子数据（企业/门店/商品/批次/历史团餐单/档案/工单/发票/月结）。设置 `SEED_ON_EMPTY=false` 可关闭。

## 核心业务流（建议按角色依次体验）

1. **企业行政** `chenguang` →「发起团餐」填写人数/餐标/素食/过敏/送达时间/发票/备用联系人 →「智能试算方案」预览 → 提交后系统综合**附近门店库存、鲜食批次、配送能力、临期商品、历史偏好、高峰时段**生成供餐方案（含方案依据与门店平衡提醒）→「确认方案并下单」。
2. **门店** `store1` →「团餐订单」开始备货 →「备货完成」：系统先在同一库存快照上核验全部方案明细（送达时仍保质、临期优先），**任一商品不足则订单与所有批次数量保持不变**，仅生成缺货协同工单并通知门店/客服；全部满足时才在一个事务里一次扣减完整批次、回写实际临期使用量、生成配送任务并进入待取货（补货/调拨后再次备货，缺货工单自动办结）。「库存与临期」可登记批次（饭团/便当/三明治/咖啡/饮料/水果 + 温控 + 保质期）、报损、发起**临期调拨**；「排班与到货」登记缺员与供应商到货（延迟自动预警）。
3. **仓配** `courier1` →「配送任务」出库登记（保温箱号、路线）→ 取货 → 送达；迟到 15 分钟以上自动生成「配送迟到」工单。
4. **企业行政**签收（记录实际人数/退货）→ 订单归档，实际消费/退货/临期调拨/赔付/发票进入**交付档案**；可提交员工反馈，勾选「餐食变质」自动生成**紧急工单**。
5. **客服** `service` / **财务** `finance` →「异常工单」在同一团餐单内协同：受理 → 留言 → 提出赔付 → 财务确认赔付 → 办结；发票错误工单联动发票标记，财务红冲重开并计入档案发票错误次数。
6. **财务** →「发票与月结」对单结企业开票；对月结企业按账期归集生成月结单 → 企业确认 → 财务开票 → 登记回款。
7. **企业行政** →「复购助手」查看历史准点率、售后次数、发票错误、餐食偏好分布，点「再次预订」自动预填上次套餐并调整后提交。
8. **送达前临时加餐（本轮新增）**：
   - **企业行政** `chenguang` 打开「我的订单」中 **40 人、约 70 分钟后送达**的已确认会议餐（种子演示单，单号 `TM…04`）→「送达前临时加餐」→ 填追加 **30 份**（可含素食、新增过敏忌口、按企业名单逐人登记特殊餐）→「核查库存与差额」。
   - 平台对**原门店 + 周边 15km 门店**逐店核查：可用批次库存（送达时仍在保质期、为原方案预留库存、临期批次优先）、当日剩余团餐产能、**配送容量**（40+30=70 超过保温箱 60 份 → 自动给出加派骑手与 ¥15 加派费）、**发票差额**（原额 → 追加后金额），输出周边门店核查明细表；原门店可承接则按原时间送达，仅周边门店可承接时送达时间顺延 15 分钟。

9. **餐食变质售后（本轮新增）**：
   - **企业员工** `chenguang` → 已送达/签收/归档订单详情 →「餐食变质/异味售后」：勾选问题商品并选择**生产批次**，确认**签收时间**，登记**温控照片**（文件名/表面℃/中心℃）与**食用人员**（姓名/电话/症状）→ 提交后自动生成 **URGENT 食安工单**并通知客服与门店。
   - **客服** `service` →「变质售后」受理后可：①**批量退款**（默认 2 倍食安赔付，可改倍数，待财务确认）；②**补送**（按问题数量生成补送单，门店用新鲜批次备货扣减、自动派骑手取货送达）；③**触发同批次门店下架**。

   - **未处理门店会被运营提醒**：任务超期自动催办（同店 30 分钟一次，通知门店与运营，行变红超时），运营/客服也可在售后详情手动「催办」。
   - **财务** `finance` →「售后退款确认」确认批量退款，金额计入交付档案赔付；**骑手** `courier1` →「配送任务」页顶部「变质餐食补送任务」取货、送达并登记签收人。
